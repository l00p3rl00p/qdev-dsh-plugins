## Why configuration alone cannot meet Feature 2

1. Every existing global form write addresses one profile plugin row; it cannot select a chat. Using it for a chat override would change other chats and violate isolation.
2. A native Session header is immutable and has no arbitrary SOUP setting fields. Specialized approval/model/preset operations are not a registration seam for arbitrary SOUP controls.
3. Native storage and session UI mechanisms already exist and are sufficient for persistence/presentation. What they do not supply is SOUP-specific sparse override semantics, effective-value resolution, safe detector application, and a human editor for those records.

Conclusion: **no configuration-only solution was established**. The platform extension mechanisms do not need replacement or expansion. The minimum justified addition is SOUP-owned behavior registered through those existing seams. This is not permission to build a new configuration/persistence subsystem or direct private code integration.

## Proposed bounded Feature 2 contract — approval required

- Keep native global defaults and the accepted global page unchanged.
- Store validated sparse overrides keyed by the exact chat SessionId using native durable storage. Record field presence explicitly: an override equal to the global value is still an override; `false` and preset `0` must not disappear through truthiness.
- Resolve every unoverridden field from CURRENT global defaults. Remove one key to revert that setting; do not copy a global snapshot into the chat record.
- Cover the actual tunables, including sensitivity and the ordinary interpreter setting where exposed to the human. The numeric threshold remains derived from the sensitivity preset; do not invent a second competing threshold source.
- The global master remains a hard cap: a chat cannot turn SOUP on while the global master is OFF. Chat changes must not modify globals or another chat.
- One Host operation owns validation, revision checks, durable writes and runtime application. Failed/stale writes must not report success or mutate the effective runtime first. Human UI only; no agent-accessible authority-loosening control is requested.
- Use an additive session-scoped settings affordance. Do not start the live Trajectory card, monitoring dashboard, plan editor or new escalation policy in this feature.
- Preserve Mentor strikes/reset decisions. Cancel stale detector work at a documented settings boundary; reseed the detector as needed without granting new intervention allowance.
- Reopening the same chat restores its overrides. A new/forked chat is a separate identity and defaults to current globals unless an inheritance requirement is separately approved; do not accidentally copy sidecars through session-log replay/export.
